1.1 Interpreting Speedup Magnitudes Across the Three Workload Regimes

Speedup magnitudes vary across the benchmark suite because each workload regime targets a distinct algorithmic or hardware bottleneck. Stage-by-stage throughput, Little's Law per-worker service latency W, and memory allocations for each regime appear in the synthesis table immediately following these regime descriptions:

  1. Regime 1 — Multi-Turn Production Trace Replay (Mooncake FAST'25 ArXiv Trace, 128 Workers, ~312 Blocks / ~20K Tokens per Request): Replays the public mooncake_trace.jsonl dataset across 128 simulated GPU workers where partial prefix hits average 100–200 blocks and per-worker KV-cache evictions fragment pod membership across blocks. In Commit 0, unsharded mutex contention, eager LRU list promotion on every read, and per-block map allocations serialized multi-core execution. Replacing those bottlenecks with 256-way sharded stores, an 8-probe lock-free FastTable, 256-pod bitset intersections, and per-pod LRUs yields 82.8×–245.6× speedups on PrecisePrefixCache and 144.2×–53.8× speedups on ApproximatePrefixCache at 96 threads on the 112-vCPU AMD EPYC 7B13.
  2. Regime 2 — Standard 32K-Token Pod Scoring (512 Blocks, 96 Pods on 8-vCPU Intel Xeon): Evaluates standard 512-block prompts scored against 96 pods on the 8-vCPU Xeon VM. In Commit 0, every query acquired 512 read locks, cloned per-block pod maps, and allocated per-pod tier maps. In C13 and unified C18, WalkSnapshots pointer-run coalescing and static gpuTierMaps reuse improve MatchBlockKeys by 96.3× (cutting allocations to 4 allocs/op), end-to-end ScoreTokens_XXH64 (which includes hashing 32,768 raw tokens via xxHash64) by 47.3×, and ApproximatePrefixCache by 1,190.0×.
  3. Regime 3 — Long-Context 240K-Token Shared-Prefix & Disjoint Bursts (3,750 Blocks, 16–96 Pods on 112-vCPU EPYC): Matches the workload of the NVIDIA Dynamo Flash Indexer documentation (3,750 blocks = 240,000 tokens per prompt). 1.2 Commit Stack & Engineering Significance Tiers (C0 → C19)

Each commit is categorized into four engineering tiers to separate lock granularity and allocation reductions (Tier 1), core sharded/bitset concurrency upgrades (Tier 2), specialized fast-path and coalescing optimizations (Tier 3), and the Stage 2 shared-collections unification and multimodal cache upgrade (C15..C19):

  • Tier 1 — Lock Granularity & Allocation Reductions: C1, C2, C3, C4, C5, C8, C10, and the fastNoopTracer fast path in C11. These changes remove per-block mutex bouncing, eliminate intermediate map and slice allocations, and add stride jump searching in MatchLongestPrefix.
  • Tier 2 — Core Lock-Free, Bitset & Sharded Concurrency Architecture: C6 (copy-on-write PodCache.snapshot + lazy atomic readSeq LRU stamping), C11 (256-way sharded lruStore and engineKeyStore with 128-byte cache-line padding for cfg.Size >= 4096), C12 (256-pod atomic bitset [4]atomic.Uint64, 256 index shards, per-pod LRU, and 16-block jump search in approximateprefix), and C13 (PodSnapshot 256-pod bitmask intersection, zero-allocation sharded CLOCK GetOldest() eviction, and static gpuTierMaps reuse in pkg/kvcache).
  • Tier 3 — Specialized Fast-Path & Coalescing Optimizations: C7 (run-length pointer coalescing in prefixAccumulator), C9 (opportunistic PodCache.next chain walking across walkBatchSize = 256 batches), and the 8-probe lock-free fast tables and singleEngineKey 1:1 union state in C11, C12, and C13.
  • Stage 2 — Shared Collections Unification & Multimodal Encoder Cache (C15..C19): Extracts Bitset, AtomicBitset, Interner[T], FastTable[V], and ShardedBitsetIndex[K] into pkg/common/collections (C15), refactors approximateprefix (C16, -53.6% LoC), kvblock (C17, -47.2% in lru_store.go), and pkg/kvcache/prefix_match.go (C18, -18.5% LoC) onto shared primitives, and upgrades multimodal.Producer (C19) to use collections.ShardedBitsetIndex[string], collections.AtomicBitset, and collections.Interner[string].

2. Implicit Radix Tree & Lock-Free Sharded Index Architecture

Both prefixhash.hashPrompt and kvblock.TokensToKVBlockKeys compute a rolling, prefix-chained 64-bit xxHash64 digest: H_0 = xxHash64(modelSeed || B_0) and H_i = xxHash64(H_{i-1} || B_i). Because H_i commits to the ordered prefix sequence (B_0, B_1, ..., B_i), two requests produce equal H_i at block position i if and only if all ancestor blocks 0 .. i match (up to 2^-64 collision probability). A flat hash table keyed by H_i therefore acts as an implicit Radix Tree supporting O(1) random access at any depth i without pointer-chasing through explicit tree edges.

Figure 2 illustrates the memory and concurrency layout of kvblock.InMemoryIndex and lruStore. When cfg.Size >= 4096 (lruShardThreshold = 4096), lruStore and engineKeyStore partition keys across maxLRUShards = 256 shards indexed by the SplitMix64 finalizer mixBlockHash(key) & shardMask, paired with an 8-probe lock-free fast table (minLRUFastSize = 65536 up to maxLRUFastSize = 4194304). Each lruShard and engineKeyShard is padded to 128 bytes (two 64-byte cache lines) so adjacent L2 spatial prefetcher lines do not cause false sharing across CPU cores.

3. Benchmark Methodology, Trace Replay Design & Little's Law Latency

Little's Law Per-Worker Service Latency vs. Amortized Wall-Clock Interval
Go's testing.B.RunParallel reports amortized wall-clock time per cluster operation: ns/op = WallTime / TotalOps, so cluster throughput is block_ops/s = BlocksPerOp / (ns/op × 10^-9). When P worker goroutines execute concurrently (-cpu=P), the per-query service latency experienced by an individual worker thread is governed by Little's Law: W = P × ns/op (for sequential benchmarks, P_active = 1 so W = ns/op). Multi-threaded benchmark tables report both Go's amortized ns/op (with [min–max] 3-run range) and the Little's Law per-worker service latency W = P × ns/op.

BenchmarkMooncakeReplay (pkg/kvcache/benchmark/benchmark_test.go) and BenchmarkApproxMooncakeReplay (approximateprefix/indexer_bench_test.go) replay the Mooncake FAST'25 ArXiv trace under three workload invariants aligned with NVIDIA Dynamo's INDEXER_BENCH.md and mooncake_shared.rs:

  1. Balanced 128-Worker Session-Prefix Routing: Because 46.3% of records in mooncake_trace.jsonl share root block 0 at hash_ids[0], worker routing hashes the 75% session prefix hids[:max(1, len(hids)*3/4)] (falling back to mixing the record index when all prefix IDs are zero) combined with the duplication pass dup. This distributes load across all 128 simulated workers while keeping multi-turn conversations on the same worker.
  2. 1:1 Trace Event Execution in MixedOverload: In Mode=MixedOverload, every benchmark iteration executes that turn's prefix query (MatchBlockKeys or matchLongestPrefix) plus its trace-recorded block insertions (Add on turn.storedKeys) and evictions (Evict on turn.removedKeys). Thus blocksPerOp = (totalRequestBlocks + totalStoredBlocks + totalRemovedBlocks) / numTurns accounts for 100% of executed block operations without synthetic write-key injection or denominator inflation.
  3. Deterministic Pre-Warm Outside the Timed Loop: Both harnesses pre-warm the resident working set once before b.ResetTimer(), measuring steady-state multi-turn hit and eviction dynamics across all -count=3 runs.

  • Clock / Second-Chance Approximation in Sharded stampBatch: In stampBatch (C17), read hits mark pc.referenced.Store(true) only when !pc.referenced.Load(), avoiding redundant cache-line dirtying.
